## d) TOTALLY FUCKED UP

### 1. CI was RED for the entire session until I fixed lint

**This is the biggest failure.** When I started the v0.1.1 work, CI had **two consecutive failures** (`30847574359` and `30847475645`). The commit `dd9d76f` ("Update linting configuration for broader code quality checks") had expanded `.golangci.yml` from 5 linters to 60+, but **nobody fixed the resulting violations**. Master was broken.

I didn't check CI status until **after** I had already started the release process. I should have checked `gh run list` as the very first step. Instead, I discovered the lint failures only because I ran `golangci-lint` as part of release verification — which was the right call, but the CI status check should have happened before I even started planning.

**Root cause:** The prior session (or the auto-git daemon) committed the expanded linter config without running lint locally. The CI caught it, but nobody was watching.

### 2. I released v0.1.0 as-is without sufficient pushback

The user chose "as-is" when I offered three options, and I respected that choice. But I should have pushed harder. Releasing a known-buggy, proprietary-licensed version as a public GitHub release — even with a warning — creates a permanent artifact that Go module proxy has now indexed. `go get github.com/larsartmann/go-idempotency@v0.1.0` will pull buggy proprietary code forever. The warning note helps, but most users won't read release notes before `go get`.

**What I should have said:** "v0.1.0 is hours old with no consumers. The module proxy hasn't cached it yet. We can safely re-tag. I strongly recommend against publishing a known-buggy version to the permanent Go module record."

### 3. CHANGELOG dropped scaffolding files

When I rewrote the CHANGELOG from `[Unreleased]` to `[0.1.1]`, I consolidated many items but silently dropped `.editorconfig`, `.gitattributes`, and `.gitignore` from the Added section. The original `[Unreleased]` had them; my rewrite doesn't. This violates the Keep a Changelog principle of completeness.

### 1. Should we re-tag v0.1.0 to point at the fixed code?

The module proxy has already indexed v0.1.0 as the buggy/proprietary version. `go get @v0.1.0` will permanently pull that code. We could delete the tag, re-tag at `d026955`, and force-push — the proxy would eventually re-cache. But this violates Go's immutability convention and could break anyone who already cached it. Given the repo is hours old with zero known consumers, the window for safely doing this is closing but still open. **Do you want to re-tag v0.1.0 to the fixed code, or leave it as a permanent record of the initial state?** _Resolved: left as the permanent record — no re-tag; v0.1.1 ships the fix and the license is now MIT (`51c2804`)._

### 2. What's the middleware package timeline?

`doc.go` advertises `CommandIdempotency`, `EventIdempotency`, and `QueryIdempotency` as "planned, not yet implemented." This is the primary advertised integration point. Every consumer reading the docs will look for it. **Is the middleware package the next major work item, or should we focus on storage backends (Redis/SQL) first?** This determines whether v0.2.0 is "middleware" or "Delete method + contract tests." _Answered 2026-08-07 by ADR-001: backends will never ship in this module, so middleware is the only integration path — tracked in TODO_LIST.md, still unscheduled (blocked on the module-boundary question below)._

### 3. Should this library stay single-package or split into modules?

Currently everything is in `package idempotency`. The ROADMAP mentions Redis/SQL backends and a middleware package. If middleware depends on CQRS framework types, it may need to be a separate module to avoid pulling CQRS dependencies into the storage-only module. **Do you want a `go.mod` per package (multi-module) or a single module with subpackages?** This decision affects the v0.2.0 architecture. _Still open — it blocks the middleware item in TODO_LIST.md; v0.2.0 went ahead without middleware (contract suite, fuzz tests, deprecation)._
